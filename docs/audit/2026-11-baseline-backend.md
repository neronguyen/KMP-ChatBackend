#### 2. Verification of Specific Server Behaviors Requested in Prompt

1. **Flat string `error` format (`ErrorCode`) on HTTP and WebSocket responses**:
   - **REST Controllers & Exception Handlers**: `CommonExceptionHandler` (`common/src/main/kotlin/io/github/neronguyenvn/nerochat/api/advice/CommonExceptionHandler.kt:37-145`), `AuthExceptionHandler` (`user/src/main/kotlin/io/github/neronguyenvn/nerochat/user/api/advice/AuthExceptionHandler.kt:23-84`), and `ChatExceptionHandler` (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/api/advice/ChatExceptionHandler.kt:17-78`) all construct `ApiErrorDto(error = <ServerError>, ...)` using the secondary constructor of `ApiErrorDto`, which delegates to `error.code` (`ErrorCode`). Spring MVC serializes `ResponseEntity<ApiErrorDto>` using `spring-boot-starter-kotlinx-serialization-json`, producing a flat JSON string (verified in `SecurityAndValidationIntegrationTest.kt:129-132,171-173`).
   - **Servlet Filters (`SecurityConfig` & `TrustedProxyFilter`)**: `SecurityConfig.kt:68-88` and `TrustedProxyFilter.kt:43-52` manually encode `ApiErrorDto(error = CommonServerError.Unauthorized, ...)` via `kotlinx.serialization.json.Json.encodeToString(errorResponse)`, preserving the flat string format. Note: `SecurityConfig.apiAccessDeniedHandler()` (`SecurityConfig.kt:79-88`) and `TrustedProxyFilter.kt:44-50` return HTTP `403 Forbidden` with `error = CommonServerError.Unauthorized` (since `CommonServerError` has no `Forbidden` entry).
   - **WebSocket Error Frames**: `ChatWebSocketHandler.sendError` (`ChatWebSocketHandler.kt:223-237`) constructs `WsServerEvent.Error(error = error, message = message, roomId = roomId, messageId = messageId)` and encodes it via `Json { classDiscriminator = WsServerEvent.CLASS_DISCRIMINATOR }.encodeToString(event)`, producing `"type":"error"` and flat string `"error":"ChatServerError.<Code>"` (verified in `ChatWebSocketHandlerTest.kt:142-145,172-179,206-209`).
2. **`EmailRequest` endpoints (`POST /api/auth/forgot-password` and `POST /api/auth/resend-verification`)**:
   - **HTTP Status**: Both endpoints (`user/src/main/kotlin/io/github/neronguyenvn/nerochat/user/api/controller/AuthController.kt:79-96,180-197`) are annotated with `@ResponseStatus(HttpStatus.NO_CONTENT)` and return **`204 No Content`** (empty body), **not** `200 OK`.
   - **Error Contracts Returned**: Both accept `@Valid @RequestBody body: EmailRequest` (validated by `ContractValidationAdvice` -> `CommonServerError.ValidationFailed` on `400 Bad Request`), are annotated with `@IpRateLimiting` (`CommonServerError.RateLimitExceeded` on `429 Too Many Requests` when `rate-limit.ip.apply-limit=true`), and execute inside `emailRateLimit(body.email)` (`CommonServerError.RateLimitExceeded` on `429 Too Many Requests`). Inside the lambda, both explicitly catch and swallow `UserNotFoundException` (`AuthController.kt:92-94,193-195`) so unknown emails still advance the email rate limiter and return `204 No Content`. Thus, neither endpoint ever returns an `AuthServerError`; they only return `204 No Content` or `CommonServerError` (`ValidationFailed`, `BadRequest`, `RateLimitExceeded`, `InternalServerError`).
   - **Side effect on already-verified user in `resend-verification`**: In `EmailVerificationService.resendVerificationEmail` (`user/src/main/kotlin/io/github/neronguyenvn/nerochat/user/service/EmailVerificationService.kt:64-68`), `createVerificationToken(email)` is called *before* checking `if (token.user.isEmailVerified) return`. Consequently, calling `/api/auth/resend-verification` for an already-verified user still invalidates prior verification tokens and persists a new unused `AuthTokenEntity` row in PostgreSQL before returning early without publishing `UserEvent.RequestResendVerification`.
3. **`CreateGroupChatRoomRequest.name` and duplicate participant UUIDs**:
   - **`CreateGroupChatRoomRequest.name` handling**: In `ChatRoomController.createGroupChatRoom` (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/api/controller/ChatRoomController.kt:113-121`), `body.name` is passed to `ChatRoomService.createGroupChatRoom` (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/service/ChatRoomService.kt:126-168`). At `ChatRoomService.kt:155`, `name = name?.trim()?.takeIf { it.isNotEmpty() }` trims leading/trailing whitespace and normalizes empty/blank strings to `null`. There is no contract or service validation on `name` length (persisted in `ChatRoomEntity.name` as nullable `VARCHAR(255)`).
   - **Duplicate participant UUIDs & creator self-inclusion**: `ContractValidationAdvice` runs `CreateGroupChatRoomRequest.validate()` first. Then `ChatRoomController.kt:119` maps `body.participantIds.map { UserId(it) }` as a `List<UserId>` into `ChatRoomService.createGroupChatRoom`. At `ChatRoomService.kt:131-135`:
     ```kotlin
     val uniqueParticipantIds = participantIds.toSet()
     val otherParticipantIds = uniqueParticipantIds - creatorId
     if (otherParticipantIds.size < 2) {
         throw InvalidChatRoomSizeException("Group chat rooms must have at least 2 other participants")
     }
     ```
     - If a request contains duplicate participant UUIDs (e.g. `["uuid-1", "uuid-1"]`) or includes the requester's own `creatorId` (e.g. `["creator-uuid", "uuid-1"]`) such that fewer than 2 distinct *other* participants remain after `.toSet() - creatorId`, the server throws `InvalidChatRoomSizeException`, which `ChatExceptionHandler.kt:44-51` maps to HTTP `400 Bad Request` with `ApiErrorDto(error = ChatServerError.InvalidChatRoomSize, message = "Group chat rooms must have at least 2 other participants")`.
     - If 2 or more distinct other participants remain alongside duplicates (e.g. `["uuid-1", "uuid-1", "uuid-2"]`), `.toSet()` silently deduplicates them and creates the 3-member group room.
   - **`AddChatParticipantRequest.userIds` duplicate handling**: `ChatRoomController.addParticipants` (`ChatRoomController.kt:148`) silently deduplicates `body.userIds.map(::UserId).toSet()` before calling `ChatRoomService.addParticipantsToChatRoom`.

## 7. Runtime & state mechanics

### 7.1 WebSocket Connect, Auth, Heartbeat & Session Lifecycle

- **Endpoint & Origin Policy**: Raw Spring `TextWebSocketHandler` registered at `/ws/chat` with `.setAllowedOriginPatterns("*")` (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/api/websocket/WebSocketConfig.kt:14-18`).
- **Filter-Layer Bypass & Handshake Auth**:
  - `SecurityConfig.kt:45` permits `/ws/**` at the HTTP filter chain, and `JwtAuthenticationFilter.shouldNotFilter` (`JwtAuthenticationFilter.kt:47-49`) skips `/ws/*`.
  - In `ChatWebSocketHandler.afterConnectionEstablished` (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/api/websocket/ChatWebSocketHandler.kt:54-97`), the server reads `session.handshakeHeaders.getFirst(HttpHeaders.AUTHORIZATION)` (`lines 55-57`). If missing or if `!jwtService.validateAccessToken(token = authHeader)`, it immediately closes the session with `CloseStatus.POLICY_VIOLATION.withReason("Authentication failed")` (`1008`, `lines 59-68`).
  - Note: Access token expiration is checked only during `afterConnectionEstablished` (`JwtService.validateAccessToken`), not on subsequent frames (`handleTextMessage`, `lines 167-221`).
- **In-Memory Session & Room Subscription State**:
  - Tracked in four node-local `ConcurrentHashMap` structures (`ChatWebSocketHandler.kt:48-51`): `sessionsById`, `sessionIdsByUserId`, `roomIdsByUserId`, and `sessionIdsByRoomId`.
  - On connect, `roomIdsByUserId.computeIfAbsent(userId)` queries `chatRoomService.findChatRoomsByUser(userId)` (`lines 85-88`) and subscribes the session to each room (`lines 90-94`). Note: if a user already has one open session, a second session reuses the cached `roomIdsByUserId[userId]` set (`computeIfAbsent`).
  - Room membership updates are synchronized in-process via `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` handlers for `ChatRoomCreatedEvent`, `ChatParticipantJoinedEvent`, `ChatParticipantLeftEvent`, and `MessageDeletedEvent` (`lines 269-333`). Note: when a room is created via REST (`onRoomCreated`, `lines 303-316`), `roomIdsByUserId` and `sessionIdsByRoomId` are updated in memory, but **no WebSocket event is broadcast for room creation** (`createDirectChatRoom` also does not broadcast its initial message over WebSocket; `ChatRoomService.kt:108-120`).
  - **Concurrency hazard**: `WebSocketSession` is stored raw without `ConcurrentWebSocketSessionDecorator` (`TODO` at `ChatWebSocketHandler.kt:72-73`), so concurrent writes from `pingClients()` (`@Scheduled`), `handleTextMessage()`, and `@TransactionalEventListener` threads can race on `session.sendMessage()`.
- **Heartbeat (Ping/Pong) & Timeout**:
  - `@Scheduled(fixedDelay = 30_000L)` `pingClients()` (`ChatWebSocketHandler.kt:127-160`, `366-367`) checks every open session: if `currentTime - lastPongTimestamp.get() > 30_000L`, it closes the session with `CloseStatus.SESSION_NOT_RELIABLE.withReason("Ping timeout")` (`4500`, `line 154`); otherwise it sends a WebSocket `PingMessage()` (`line 142`). `handlePongMessage` updates `lastPongTimestamp` (`lines 162-165`).

### 7.2 Idempotency of Message Sending & Direct Room Creation

- **WebSocket `NewMessage` Idempotency** (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/service/ChatMessageService.kt:52-96`):
  - `WsClientMessage.NewMessage.messageId` is optional (`String? = null`).
  - When `messageId != null`, `ChatMessageService.sendMessage` looks up `chatMessageRepository.findByIdOrNull(targetMessageUuid)` (`lines 67-76`):
    - If found with the **same `roomId` and `sender.userId`**, it returns `existingMessage.asExternalModel()` without inserting or re-publishing `ChatEvent.NewMessage` to RabbitMQ (`lines 71-73`), and `ChatWebSocketHandler.kt:263-266` re-broadcasts `WsServerEvent.NewMessage` to the room.
    - If found with a **different `roomId` or `sender.userId`**, it throws `DuplicateMessageIdException(messageId)` (`line 74`), which `ChatWebSocketHandler.kt:204-211` maps to `WsServerEvent.Error(error = ChatServerError.DuplicateMessageId, roomId = ..., messageId = ...)`.
  - When `messageId == null`, the server generates a UUIDv7 (`Uuid.generateV7().toJavaUuid()`, `ChatMessageService.kt:80`).
  - `ChatMessageEntity` implements `Persistable<UUID>` with `@Transient private var isNewEntity: Boolean = true` (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/infra/database/model/ChatMessageEntity.kt:62-80`) so Spring Data JPA executes `EntityManager.persist()` (SQL `INSERT`) instead of `merge()` even when a client-assigned `id` is supplied, preventing silent overwrites on primary-key collision.
- **Direct Chat Room Idempotency** (`chat/src/main/kotlin/io/github/neronguyenvn/nerochat/chat/service/ChatRoomService.kt:68-123`):
  - Computes canonical `DirectPairKey` (`min(userA, userB)_max(userA, userB)`, `DirectPairKey.kt:9-14`), backed by unique index `idx_chat_room_direct_pair_key` on `chat_service.chat_rooms(direct_pair_key)` (`ChatRoomEntity.kt:32-36`).
  - If `findDirectChatRoomBetween(directPairKey)` finds an existing room, `createDirectChatRoom` returns the existing room (with its existing `lastMessage`, ignoring the new `message` parameter in the request) without creating a duplicate room (`ChatRoomService.kt:84-93`).
  - Concurrent creation race condition is noted as an open `TODO` at `ChatRoomService.kt:95-98` (an unhandled `DataIntegrityViolationException` bubbles to `CommonExceptionHandler.onUnhandledException` as `500 CommonServerError.InternalServerError`).

### 7.3 Ordering & Pagination

- **Timestamp Precision & Tie-Breaking**:
  - `ChatMessageEntity.createdAt` is truncated to milliseconds both at initialization and in `@PrePersist` (`createdAt.truncatedTo(ChronoUnit.MILLIS)`, `ChatMessageEntity.kt:61,71-74`).
  - Database index `idx_chat_message_chat_room_id_created_at` is defined on `(chat_room_id, created_at DESC, id DESC)` (`ChatMessageEntity.kt:34-37`).
  - All message queries (`findByRoomId`, `findByRoomIdBefore`, `findLatestMessagesByRoomIds` in `ChatMessageRepository.kt:13-58`) order deterministically by `ORDER BY m.createdAt DESC, m.id DESC` (leveraging monotonic UUIDv7 IDs for sub-millisecond tie-breaking).
- **Cursor Pagination (`GET /api/chat/rooms/{roomId}/messages`)**:
  - Fixed page size `DEFAULT_PAGE_SIZE = 20` (`ChatMessageService.kt:134,155`); no `limit` query parameter is exposed on `ChatRoomController.getChatMessages` (`ChatRoomController.kt:68-71`, despite `PostmanCollectionGenerator.kt:191` having a sample rule for `"limit"`).
  - When `before == null`, queries latest 20 messages (`findByRoomId`). When `before != null`, truncates `before` to milliseconds and queries `m.createdAt < :before` (`findByRoomIdBefore`, `ChatMessageRepository.kt:33`). Note: because the cursor filter uses strict inequality `m.createdAt < :before` without a composite `(createdAt, id)` cursor, two messages in the exact same millisecond at a 20-message page boundary would both be excluded by `createdAt < :before`.
  - Repository returns `Slice<ChatMessageEntity>` in `DESC` order; `ChatMessageService.kt:148-151` reverses the slice (`slice.content.asReversed()`) so `ChatMessageSliceDto.messages` is returned in chronological (`ASC`) order with `hasMore = slice.hasNext()`.
- **Room List Ordering**:
  - `ChatRoomService.findChatRoomsByUser` (`ChatRoomService.kt:51-65`) sorts rooms in memory via `.sortedByDescending { it.lastActivityAt }`, where `lastActivityAt` is `lastMessage?.createdAt ?: createdAt.toKotlinInstant()` (`ChatRoomEntity.kt:95`).

### 7.4 Persistence, Caching & Messaging Infrastructure

- **PostgreSQL (JPA / Hibernate)**:
  - Configured via `spring.datasource.*` (`app/src/main/resources/application.yaml:8-25`).
  - Uses two PostgreSQL schemas:
    - `user_service`: `users` (`UserEntity.kt:11-18`), `refresh_tokens` (`RefreshTokenEntity.kt:10-17`), `auth_tokens` (`AuthTokenEntity.kt:10-13`).
    - `chat_service`: `chat_participants` (`ChatParticipantEntity.kt:11-17`), `chat_rooms` (`ChatRoomEntity.kt:28-38`), `chat_room_participants_cross_ref` (`ChatRoomEntity.kt:59-80`), `chat_messages` (`ChatMessageEntity.kt:30-39`).
  - No Flyway or Liquibase migrations exist (`chat/src/main/resources/db/migration` is an empty directory); `application-dev.yaml:4` uses `ddl-auto: update` and `application-prod.yaml:4` uses `ddl-auto: validate`.
  - Refresh tokens are stored as SHA-256 Base64 hashes (`AuthService.kt:186-190`) in `user_service.refresh_tokens`. Note: `AuthService.refreshToken` (`AuthService.kt:114,121-147`) checks JWT expiration (`jwtService.validateRefreshToken`) and deletes the matching DB row, but does not check `RefreshTokenEntity.expiredAt`, and `TokenPurgeService` (`TokenPurgeService.kt:14-19`) only purges `AuthTokenEntity` (`user_service.auth_tokens`), never `RefreshTokenEntity` (`user_service.refresh_tokens`).
- **Redis (Redisson)**:
  - Configured via `spring.redis.redisson.config` (`application.yaml:31-41`) and `RedisConfig.kt:12-37`.
  - Used for:
    1. **Message slice cache**: `RedissonSpringCacheManager` cache `"messages"` (`CacheNames.MESSAGES`) with 30-minute TTL (`RedisConfig.kt:20-35`). Caches `ChatMessageSliceDto` keyed by `ChatRoomId` only when `before == null` (`ChatMessageService.kt:124-129`); evicted on `sendMessage` (`@CacheEvict`, `lines 48-51`) and `deleteMessage` (`lines 119-121`).
    2. **Distributed IP rate limiting**: `IpRateLimitingService` (`IpRateLimitingService.kt:23-66`) uses Redisson lock `lock:ip:<ip>:<Controller>:<method>` (3s wait, 5s lease) and atomic counter `rate_limit:ip:<ip>:<Controller>:<method>` (default 10 requests / 1 hour per `@IpRateLimiting`, `IpRateLimiting.kt:5-9`). Disabled in `dev` (`rate-limit.ip.apply-limit: false`, `application-dev.yaml:19-21`), enabled in `prod` (`application-prod.yaml:19-21`).
    3. **Distributed Email rate limiting**: `EmailRateLimitingService` (`EmailRateLimitingService.kt:23-68`) uses Redisson lock `lock:email:<email>` (5s wait, 10s lease), bucket `rate_limit:email:<email>`, and counter `attempt_count:email:<email>` with progressive cooldowns of `60s`, `300s`, and `3600s` (24h counter reset). Always active on `/api/auth/resend-verification` and `/api/auth/forgot-password` regardless of `rate-limit.ip.apply-limit`.
- **RabbitMQ (AMQP)**:
  - Configured in `application.yaml:46-72` (`ssl.enabled: true`, 3x retry with exponential backoff `1000ms` -> `10000ms`) and `RabbitMqConfig.kt:14-84`.
  - Uses custom `KotlinSerializationJsonAmqpMessageConverter` (`common/src/main/kotlin/io/github/neronguyenvn/nerochat/infra/messagequeue/KotlinSerializationJsonAmqpMessageConverter.kt:9-50`) with `Json { classDiscriminator = "type" }` over polymorphic `Event` hierarchy (`UserEvent`, `ChatEvent`).
  - `EventPublisher.publish(event)` (`EventPublisher.kt:18-43`) registers a Spring `TransactionSynchronization.afterCommit()` callback when an active transaction exists so AMQP messages are only sent after DB commit (swallowing and logging any `RabbitTemplate` exception in `sendDirect`, `lines 32-43`).
  - Exchanges & Queues (`RabbitMqConfig.kt:34-83`):
    - Topic exchange `user.events`:
      - Queue `notification-service-for-user-events` bound with routing key `user.*` -> consumed by `NotificationUserEventListener` (`NotificationUserEventListener.kt:18-45`) to send verification/reset emails via `EmailService`.
      - Queue `chat-service-for-user-events` bound with routing key `user.verified` -> consumed by `ChatUserEventListener` (`ChatUserEventListener.kt:13-25`) to create `ChatParticipantEntity`.
    - Topic exchange `chat.events`:
      - Published to by `ChatMessageService.sendMessage` (`ChatEvent.NewMessage` with routing key `chat.new_message`, `ChatMessageService.kt:87-93`), **but no queue or `@RabbitListener` is bound to `chat.events` anywhere in `KMP-ChatBackend`**.

### 11.3 Resolved Decisions (Post-Audit Alignment)
